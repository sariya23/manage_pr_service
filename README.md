## Описание проекта

Сервис для автоматического назначения ревьюеров на 
Pull Request’ы внутри команды. 

Предоставляет REST-API для:
- назначения и переназначения ревьюверов;
- управления командами и пользователями
- получения списка PR’ов;
- назначенных конкретному участнику.

## Технические фичи

- Слоистая архитектура
- Логирование
- Высокое покрытие интеграционными тестами
- Гибкая конфигурация под различные окружения
- Использование автоген моделей (`oapi-codegen`)
- Настроенные линтеры
- Запуск юнит-тестов и линтеров в GitHub Actions
-

## Сборка проекта

### LOCAL окружение

В окружении LOCAL все компоненты запускаются в docker-контейнерах.
Окружение применяется для демонстрации работы сервиса на других компьютерах

- `make service_up` - поднять сервис
- `make service_down` - "убить" сервис

По умолчанию сервис работает на порте `8080`

### DEV окружение

В окружении DEV в docker-контейнерах запускается только инфа (БД, Kafka, redis и тд).
Применяется для локальной разработки/дебага

- `make run` - запустить севрер 
- `make infra` - поднять инфру
- `make migrate` - накатить миграции
- `make test` - запуск юнит-тестов

### TEST окружение

В окружении TEST все компоненты запускаются в docker-контейнерах.
Окружение применяется для запуска интеграционных тестов

- `make test_service_up` - поднять сервис
- `make test_integrations` - запустить интеграционные тесты
- `make test_service_down` - "убить" сервис

## Результаты нагрузочного тестирование

Для нагрузочного тестирования я выбрал Yandex Tank. Грузить буду только гетовые ручки:
`users/getReview` и `/team/get`. 

Конфигурацию можно посмотреть в файле `./load.yaml`. 

![Результаты нагрузки](https://github.com/sariya23/manage_pr_service/blob/master/doc/overload.png)

При пиковом RPS 10 сервис продолжал отвечать в пределах условий <300мс. 
Также нет ни одного запроса, который затаймаутил. 

В базе было 500 пользователей и 170 команд.

## Вопросы/проблемы

### team/add

Не совсем из описания понятно, что ручка должна делать. 
Я решил реализовать ее по такому алгоритмы алгоритму:
1) Проверить, существует ли команда
2) Если существует
    1) Проверить, что переданы только новые айдишники. 
       2) Если есть старый айди - вернуть ошибку
3) Пройтись по айдишникам
    1) Если пользователь isActive=false, вернуть ошибку
    2) Если пользователь существует
        1) Проверить, не сосотоит ли он в другой команде. Если состоит - вернуть ошибку
Этот алгоритм далее позволяет атомарно и вставить пользователей, и создать команду, так как
все проверки целостности данных и бизенс-правил выполнены

Я не хотел, чтобы она еще и обновляла пользователей, так как она
и так делает слишком много. 

## Предложения по улучшению

- Сделать ручку `/pullRequest/merge` методом `PATCH`
- - Сделать ручку `/pullRequest/reassign` методом `PATCH`
- Распилить ручку `/team/add`. Создание пользователей вынести в новую
ручку `/users/create`. Так будет разделение логики работы, потому что
текущая реализация отвечает за слишком много, что приводит к более сложному коду и 
нужно тратить больше времени на написание тестов
- Ручка для аналитики пока что выполняется быстро, но с ростом пользователей
и Pull Request'ов выполнение будет все дольше и дольше. Это приведет к деградации скорости для всех пользователей.
Избежать это можно несколькими способами:
  - Сделать мат. вью на аналитический запрос и рефрешить его каждый N момент времени
какой-нибудь джобой или расширением постгреса
  - Батчами выгружать данные каждый день в Clickhouse или другую СУБД для аналитики.
- Добавить в пайпдайн джобу по ручному запуску интеграционных тестов при PullRequest
